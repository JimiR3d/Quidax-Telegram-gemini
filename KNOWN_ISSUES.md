# PulseDesk: Known Issues & Pending Features

This document provides a brutally honest, exhaustive tracking of every bug, suspected bug, untested area, repeated fix, and pending feature in the PulseDesk application.

## 1. Repeated Fixes & Chronic Bugs
*   **LLM Schema Hallucinations:** The Groq/LLaMA integration has repeatedly returned JSON payloads with incorrect keys (e.g., `priority` instead of `urgency`) or varying casing. This was patched multiple times: first with stricter system prompts, then with Zod validation, and finally with a custom `normalizeCategory` fallback function. It remains an area of fragility if the model updates or shifts behavior.
*   **Supabase Row Level Security (RLS) Conflicts:** Initially, the backend attempted to insert records using the `SUPABASE_ANON_KEY`, which failed because RLS policies blocked anonymous inserts. This was fixed by exclusively using `SUPABASE_SERVICE_ROLE_KEY` on the backend, but any future frontend direct-database writes will instantly hit this wall if not properly scoped.
*   **AI Context Degradation:** Development environments (like AI agents) repeatedly lost the context of the project or hallucinated previous fixes because temporary build artifacts and test scripts polluted the context window. This required aggressive `.gitignore` management and manual context handoffs.

## 2. BUGS (confirmed)
*   **~~Admin reply duplication~~ — FIXED (2026-06-11):** Admin replies appeared 2-3x (up to 23x in the worst ticket) in the dashboard stream. Root cause: the duplicate-message check inside `processAndIngestMessage` ran *after* the reply-handling branches, so the AutoFetch periodic re-scan (every 15 min, 2-hour window) and manual backfills re-appended `[ADMIN_REPLY]`/`[USER_REPLY]` blocks to tickets on every pass. Fix (commit `3b04b54`): moved the `telegram_message_id` dedup check to the top of the function before any branch, and user replies are now recorded in the `messages` table so re-processing catches them too. Existing data was cleaned: 446 duplicate blocks removed across 82 tickets via a previewed-then-applied script; a re-scan confirmed zero duplicates remain.
*   **~~KPI cards unverified~~ — AUDITED & FIXED (2026-06-11, commit `2ea6bea`):** Full audit against ground-truth DB counts found: (a) "Resolved" metrics counted 481 Dismissed spam tickets as resolutions, inflating Resolution Rate from a true 53% to 80%; (b) "Resolved Today" was meaningless — it read `updated_at`, which no code ever maintained (797 of 822 tickets shared a one-off backfill date of 2026-06-09), while the dedicated `resolved_at` column was populated on 0 tickets; (c) "today" used the server's timezone (UTC on Railway) instead of Lagos. Fixed by product decision (Option A): Resolution Rate = Resolved ÷ (Resolved + Active) with Dismissed excluded everywhere; all four status-writing code paths now stamp `resolved_at`/`updated_at`; "today" computed in Africa/Lagos. Verified live: rate 80%→53%, Resolved All Time 661→180, and a resolve/reopen round-trip correctly ticked Resolved Today 0→1→0. Note: legacy tickets resolved before this fix have `resolved_at = null` and are intentionally never counted in "Resolved Today" (no fabricated timestamps).
*   **~~Avg Response Time KPI does not exist~~ — FIXED (2026-06-12, Milestone 2):** A `first_admin_reply_at` column was added (migration 009, applied to the live DB with explicit confirmation). Both admin-reply attachment paths (quoted reply and the 90-second heuristic) stamp it once, using the reply message's own timestamp so backfills stay accurate, and never move it on later replies. The dashboard now shows an "Avg Response Time" KPI card = mean of (first admin reply − ticket creation) over tickets that have a tracked reply, respecting all base filters. Legacy tickets keep `first_admin_reply_at = null` and are excluded — same no-fabricated-timestamps precedent as `resolved_at`. Verified end-to-end 2026-06-12 (measured 23s on a simulated ticket, `avgResponseMs` confirmed in the stats payload, test data cleaned up).
*   **~~Filter inconsistency~~ — AUDITED & FIXED (2026-06-11, commit `9c2ea4f`):** The audit proved category/urgency/date filters already updated the KPI cards. The real bugs: (a) the search box filtered the table but not the KPI cards (103 table rows vs 822 stats rows, live evidence); (b) custom date ranges silently dropped the whole end day ("today→today" returned 0 while 4 tickets existed today); (c) "last N days" cut at server-clock midnight (UTC on Railway) instead of Lagos. Fixed: search now lives in the shared base filters; all date boundaries are Lagos calendar days. Verified live against a server running TZ=UTC. The `status` filter intentionally stays table-only (KPI cards break down by status).

## 3. ARCHITECTURE GAPS & Suspected Bugs
*   **~~Stats query 5,000-row cap~~ — FIXED (2026-06-12, Milestone 4):** KPI aggregation moved into Postgres (`tickets_stats` function, migration 012) over the full filtered set; `/api/tickets` calls it via RPC and no longer ships raw rows (`rawStatsData` removed — the volume chart now uses the function's `volumeByDay` series, bucketed by Lagos day). Parity with the old in-memory numbers proven across 7 live filter combinations before the old code was deleted.
*   **~~Resolution detection is unreliable for unquoted admin replies~~ — MITIGATED (2026-06-11, commit `6c66bf2`):** A 90-second window heuristic now attaches an unquoted admin message to the most recently ingested Open/In Review ticket in the same group (marking it "In Review") when that ticket arrived within the previous 90 seconds. Remaining limitation, accepted by design: if several users post within the same 90 seconds, the reply attaches to the newest ticket, which may be the wrong one. (The second limitation this entry used to carry — the async classifier overwriting "In Review" — was FIXED 2026-06-12, see below.)
*   **~~Async classification overwrites statuses set during the ~5-10s window~~ — FIXED (2026-06-12, Milestone 4):** the background classifier's final update is guarded: it writes status only if the status is still exactly what ingestion inserted (atomic conditional update); if an admin reply, user reply, or dashboard action changed the status mid-classification, the classifier saves category/summary/urgency/reply WITHOUT touching status. All three write sites covered (Groq, Gemini fallback, failure path). Proven with a live race test: "Escalated" set during classification survived, classification fields still landed.
*   **~~Binary Resolution Status~~ — FIXED (2026-06-12, Milestone 2):** Tickets now support a 4-state active workflow: Open / In Review / Escalated / Awaiting User (plus Resolved and Dismissed). The DB CHECK constraint was widened (migration 009). Rules: an admin reply moves Open → In Review but never un-escalates (Escalated and Awaiting User keep their state); a user reply to an Awaiting User ticket flips it back to In Review; all four active states accept incoming replies and count as "Active" in the resolution rate denominator. The "In Review" KPI card now shows the true In Review count (it previously mislabeled it `escalatedCount`) with an escalated/awaiting-user breakdown beneath it. Verified end-to-end 2026-06-12 via `/api/ingest` simulations; invalid statuses still rejected with 400.
*   **Nigerian Pidgin English:** This is not accounted for in the classification system — common phrases like "e don do", "e never enter", "dem block my account" may be misclassified.
*   **Keyword Learning System:** The `learned_keywords` system exists but its long-term effectiveness has not been measured or verified in a live, prolonged production environment to prove it actually improves accuracy.
*   **GramJS Session Expiry:** The `TELEGRAM_SESSION_STRING` is currently treated as permanent. It has never been tested against Telegram's forced session revocations or expiry intervals. If it expires, the listener will silently die without auto-recovery.
*   **Extreme High-Volume Concurrency:** The async ingestion pipeline and heavy limiters work for standard volume. It is highly suspected that a massive raid or spam attack (e.g., 5,000 messages in 10 seconds) could overwhelm the Groq rate limits, causing the backend to start dropping messages despite the circuit breaker.
*   **Cloud Run / Railway Deployment:** GramJS requires a persistent TCP connection (WebSocket), which traditionally conflicts with serverless environments like Vercel. While containerization (Cloud Run / Railway) works in theory, long-running persistent connections often get severed by load balancers after 30-60 minutes unless active keep-alives are meticulously tuned. This tuning is currently unverified.
*   **~~Gemini 503 "high demand" errors leave tickets without a suggested reply~~ — FIXED (2026-06-12, Milestone 4):** `generateSuggestedReply` now retries capacity errors (429/5xx, "high demand", timeouts) up to 3 times with exponential backoff + jitter — each attempt is a separate circuit-breaker call, and a breaker-open fast-fail is never retried. Backstop for outages that outlive the retries: a sweep every 15 minutes regenerates missing replies on classified ACTIVE tickets from the last 24h (max 10 per run; never overwrites a reply that appeared in the meantime). Verified live end-to-end; the 661 historical null-reply tickets (resolved/dismissed/old) are deliberately out of scope. "Missing suggested reply" is now a ≤15-minute condition, not a permanent one.

## 5. Milestone 3 known limitations (accepted by design, 2026-06-12)
*   **Few-shot similarity is naive keyword overlap** (lowercased words ≥4 chars, stopword-filtered, capped at 200 candidate corrections). No embeddings/semantic match — Pidgin spelling variants ("withdraw" vs "widthdraw" vs "remove my money") won't match each other. Good enough at current volume; revisit with embeddings if corrections grow past a few hundred.
*   **A wrong admin-reply correction propagates:** if the Groq audit misreads an admin reply and "corrects" a ticket wrongly, that wrong example is injected into future similar classifications until a human fixes the ticket again in /train (a later human_ui correction wins on recency in few-shot dedupe, and a human can re-correct the ticket there only if it has no human_ui row yet — otherwise fix the category from the main dashboard... note: there is no dashboard category editor yet, so the fix is deleting the bad corrections row in Supabase).
*   **Tickets corrected via admin_reply are skipped by /train** (any corrections row counts as "reviewed"). Deliberate: the human loop should focus on tickets no one has looked at.
*   **`/api/eval` benchmark does NOT use few-shot corrections** — it stays a raw-model baseline so accuracy numbers are comparable across time. The live pipeline and `/api/test-message` DO use them.
*   **Re-classification only touches `category`** — urgency/product_area/summary are never revised by an admin reply, and status is never changed by the re-classifier.
*   **The 5-10s classification race now has a 12s retry** in `reclassifyFromAdminReply` (waits once for the classifier to settle, then skips if still pending). The status half of that race (classifier overwriting "In Review") was fixed in Milestone 4 (2026-06-12) — see section 3.

## 7. Milestone 5 (status update bot) — rollout state & v1 limitations (2026-06-12)
*   **PARKED — BLOCKED BY TELEGRAM, NOT BY CODE (2026-06-12 evening).** Phase B passed in production: with `BOT_REPLIES_ENABLED=true` + dry-run, a real status change produced exactly one correct `bot_replies` row (right target message, right group, exact template, all rails held). Phase C failed at the first live send: `400: USER_BANNED_IN_CHANNEL` — the GramJS session account is banned/muted from SENDING in OfficialQuidaxCommunity (reading/ingestion is unaffected). Nothing was posted to the group; the failure was recorded cleanly. `BOT_REPLIES_ENABLED` is back to false on Railway and the feature is parked until the account is unmuted or replaced with one that has send rights (a different account means a new session string — explicit instruction required). **Dry-run can structurally never catch this class of failure** (it never calls Telegram). One burned pair exists: the failed row blocks (ticket `0c72808f-1112-4dd7-aaa1-ed5ad2f9e938`, "Awaiting User") forever — delete that row before any retry.
*   **Failed sends are never auto-retried** (deliberate v1): the claim row in `bot_replies` stays `result='failed'` and permanently blocks that (ticket, status) pair — visible in logs and the table. If a retry is ever wanted, delete the failed row manually; an automated repair could later join the 15-minute sweep.
*   **Once per (ticket, status), EVER** (product decision): resolve → reopen → resolve again posts nothing the second time. Status flapping can never spam the group.
*   **Tickets older than 7 days never get a reply** — bulk backlog cleanup is silent by design. The bound is a code constant (`BOT_REPLY_MAX_TICKET_AGE_DAYS`).
*   **Replies come from the session user account, not a bot account**, with a deliberately neutral voice (no "Quidax Support" signature) since the account is not officially sanctioned to speak for Quidax.
*   **The dashboard gets no feedback** about whether a bot reply was sent/skipped — outcomes live in server logs and the `bot_replies` table only (v1 scope cut).

## 8. Future Enhancements
*   **Conversation threading:** PulseDesk currently treats each Telegram message as a potential individual ticket. Real support conversations often span 10–20 back-and-forth messages between a user and admin without quoting. A future version should detect conversation threads (same user, same time window) and group them as a single ticket with a full thread view. This would significantly improve classification accuracy since the AI would see full context rather than isolated messages.
