# PulseDesk Agent Rules

## Stack
Node.js + Express + TypeScript (server.ts), React 19 + Vite + Tailwind v4 (src/App.tsx), Supabase service role key only, Groq for classification, Gemini for replies, GramJS for Telegram.

## Before every task
Read PULSEDESK_HANDOFF.md and PRD.md first. Restate the task, list which files will change, identify risks. Wait for approval before acting on anything non-trivial.

## Rules
- Smallest change only — never touch unrelated files
- Never use SUPABASE_ANON_KEY for backend operations
- Never expose API keys to the frontend
- Never change DB schema without explicit confirmation
- Never regenerate the GramJS session string without explicit instruction
- One task at a time — complete and confirm before moving to the next
- All Git and PR descriptions in plain English a non-developer can understand

## End of every session
Update PULSEDESK_HANDOFF.md, KNOWN_ISSUES.md, and PRD.md. Summarize what was done and what is pending.

## Lessons learned
- **Local test runs on port 3100 can leave background processes holding the port between bash calls** — if a test server seems missing or curl hangs, always check for and kill lingering node processes on that port before starting a new one (PowerShell: `netstat -ano | Select-String ":3100"` → `Stop-Process -Id <pid> -Force`).
- **Three overlapping ingestion paths:** live listener, AutoFetch (startup + every 15 min, 2-hour lookback), and manual backfill all call `processAndIngestMessage`. Any mutation inside that function MUST be idempotent — the `telegram_message_id` dedup check must stay at the very top, before any branch that writes.
- **`tickets.updated_at` is NOT auto-maintained** — there is no DB trigger; code must set it explicitly on every update. `resolved_at` is the source of truth for when a ticket was closed; reopening clears it. Legacy tickets resolved before 2026-06-11 have `resolved_at = null` by design.
- **Resolution Rate definition (product decision, 2026-06-11):** Resolved ÷ (Resolved + Active). Dismissed tickets are spam/chatter, never counted as resolutions anywhere.
- **"Today" KPIs use Africa/Lagos**, not server time (Railway runs UTC).
- **The reconstructed migration files do not match the live schema** — always verify columns against the live DB before trusting `supabase/migrations/`.
- **Local testing runs on PORT=3100** (port 3000 is occupied by an unrelated MCP tool). Shell env vars override `.env` because dotenv does not override existing vars.
- **`/api/tickets` filter split:** `applyBaseFilters` (group, issues_only, dates, search) is shared by the table and stats queries; `status` is deliberately table-only because the KPI cards break tickets down by status. All date boundaries are Lagos calendar days — never use server-clock midnight.
- **`/api/ingest` (super_admin) accepts `isAdmin`, `msgDate`, and `replyToMsgId`** — use it to simulate admin replies, historical timestamps, and quoted reply threads when testing ingestion heuristics end-to-end. Always clean up test tickets/messages by `telegram_message_id` afterward (deleting the `messages` row cascades to the ticket via FK), and guard against attaching test admin replies to real live tickets (check no newer Open ticket exists first).
- **4-state workflow semantics (Milestone 2, 2026-06-12):** Active statuses are Open / In Review / Escalated / Awaiting User. An admin reply moves Open → In Review but NEVER changes Escalated, Awaiting User, or Resolved; a user reply to an Awaiting User ticket flips it to In Review; all four active states accept replies and count in the resolution-rate denominator. `first_admin_reply_at` is stamped exactly once, with the reply message's own timestamp (not now()), so backfills stay accurate — never overwrite it.
- **Production runs only ONE GramJS session at a time.** Railway and Fly.io must never both be live (the `telegram_message_id` dedup check is not concurrency-safe; only the DB UNIQUE constraint catches the race). Stop the old platform before deploying the new one — startup AutoFetch's 2-hour lookback recovers messages missed during the gap. Same caution applies to local testing while production is live: keep the window short.
- **Railway runs `node dist/server.mjs` via railway.toml, not `npm start`** — the npm script has a Windows-only `chcp` command. Keep `numReplicas = 1`: each replica opens its own GramJS session and double-ingests.
- **Async classification can overwrite statuses set by reply-attachment** (~5-10s race): if an admin reply lands before Groq classifies the parent ticket, "In Review" can be clobbered back to "Open"/"Dismissed". Known, documented in KNOWN_ISSUES.
- **Corrections semantics (Milestone 3, 2026-06-12):** a `corrections` row with `original_category = correct_category` means a human CONFIRMED the AI — that is how /train marks tickets reviewed; any corrections row (either source) makes /train skip the ticket. `reclassifyFromAdminReply` requires an exact case-insensitive category match from the model — never reintroduce a `normalizeCategory` fallback there, it would default hallucinations to "General Question" and rewrite real tickets.
- **Bug 4 / auto-resolve (2026-06-14):** `reclassifyFromAdminReply` NO LONGER touches only `category`. Its Groq prompt (`RECLASSIFY_SYSTEM_PROMPT`) now also returns `{resolved: bool}`, and an affirmative/definitive admin answer ("Yes, you can…", "It's done") auto-resolves the ticket. The status write is GUARDED by `shouldResolveFromAdminReply` (pure module `admin-reply-resolution.ts`) to active queue states ONLY — `Open`/`In Review` (the `AUTO_RESOLVABLE_STATUSES` array) — and applied as a CONDITIONAL update (`.in("status", AUTO_RESOLVABLE_STATUSES)`) so it can NEVER un-park an `Escalated`/`Awaiting User` ticket a human set, nor re-touch `Resolved`/`Dismissed`, nor lose a concurrent dashboard change (same defense as the Milestone 4 race fix). `resolved_at` is stamped on auto-resolve. The category branch was restructured to log-and-continue (not early-return) so a category hiccup never blocks the resolve. `resolved` is strict-true only (a missing/garbage field never resolves). Bug 4 also added a feature-existence rule to `GROQ_SYSTEM_PROMPT` ("can I…?"/"is it possible to…?" with no problem → General Question, not Trading/Withdrawal/Deposit) + benchmark cases 19-20 — base-prompt, NOT few-shot, so it reaches `/api/eval` like the Pidgin glossary.
- **Bug 3 / admin-message drop (2026-06-14, `cda3ebc`):** `checkIsAdmin` runs correctly on all ingestion paths — admin messages are now dropped when unattached (never become tickets). Don't re-investigate detection if you see admin-related issues; check the downstream drop guard in `admin-message-policy.ts` (`disposeUnattachedMessage`, called before the ticket insert in `processAndIngestMessage`) instead.
- **Few-shot injection lives in the main pipeline, the Gemini fallback, and `/api/test-message` — but deliberately NOT `/api/eval`**, which stays a raw-model baseline for comparable benchmark numbers. Deleting a ticket cascades its corrections (FK), so cleaning up test tickets also removes their few-shot examples — always verify the `corrections` count after test cleanup.
- **`*.mjs` is globally gitignored** (one-off test scripts convention). `scripts/dev-no-telegram.mjs` is therefore untracked — it blanks `TELEGRAM_SESSION_STRING` and sets PORT=3100 before importing server.ts, making local testing safe while Railway production is live. PowerShell cannot set an env var to empty (`$env:X=""` deletes it) — use that launcher or Git Bash.
- **Hosting decision (2026-06-12): staying on Railway** — Fly.io requires a payment method. The Fly config was removed in commit `510cb0c`; recover it from git history if ever needed.
- **Local server serves a STALE `dist/` build if one exists** — server.ts prefers `dist/index.html` over Vite middleware, so frontend edits are invisible until `npm run build`. When verifying UI changes locally, rebuild first (a browser reload then picks up the new bundle; the server reads dist from disk per request, no restart needed).
- **KPI stats come from the `tickets_stats` Postgres function (migration 012, Milestone 4)** — `/api/tickets` passes the base filters as RPC params and merges the returned jsonb into the stats payload; `resolutionRate`/`resolutionData`/`totalCount` are still computed in JS. The volume chart reads `stats.volumeByDay` (Lagos-day buckets); `rawStatsData` no longer exists. Any new KPI must be added inside the SQL function, not as a JS row-scan, and any new base filter must reach BOTH the table query and the RPC params.
- **`/api/verify` (Milestone 4) measures training-loop accuracy with leave-one-out** — `getFewShotCorrections(supabase, text, excludeMessageText)` skips rows matching `excludeMessageText` so a verified message never sees its own stored correction. Never drop that third argument from the verify path: without it the few-shot pool leaks the answer and the "with training" score is meaningless.
- **The async classifier writes status through a guarded conditional update (Milestone 4)** — `applyClassification` updates WITH status only where `status = insertedStatus` (atomic), else writes fields without status. All three classifier write sites (Groq, Gemini fallback, failure) must keep using it; a plain `.update({status})` there reintroduces the race where the classifier clobbers "In Review"/"Escalated" set during the ~5-10s window.
- **`isRetryableLLMError` treats `[Timeout]` from `withTimeout` as retryable** — discovered live when the first sweep test timed out and was wrongly classified non-retryable (regex said "timed out", our wrapper throws "[Timeout]"). Retry only 429/5xx/capacity/timeout errors; never a breaker-open fast-fail ("[CircuitBreaker]"), never other 4xx.
- **`messages.telegram_message_id` is BIGINT in the live DB while `tickets.telegram_message_id` is TEXT** — another reconstructed-migrations mismatch. Raw SQL against `messages` needs numeric literals or casts; supabase-js string filters work because PostgREST casts.
- **The reply-repair sweep (every 15 min) only touches tickets that are <24h old, ACTIVE status, classified, non-admin, with `suggested_reply IS NULL`** — and its update is guarded on still-null so it never overwrites an agent's edit. The bound was verified against live data (0 of 661 historical null-reply tickets matched). Widening any of those bounds risks a Gemini-quota burn on history.
- **Outbound bot rails (Milestone 5, 2026-06-12):** `maybeSendStatusBotReply` is the ONLY code that posts to the group, triggered ONLY by `POST /api/tickets/:id/status`. Both env flags must stay fail-safe: `BOT_REPLIES_ENABLED` defaults OFF, `BOT_REPLIES_DRY_RUN` defaults ON (`!== "false"`). Dedup is claim-then-send: a `bot_replies` row (result `pending`) is inserted BEFORE Telegram is called, and the partial unique index `(ticket_id, status) WHERE dry_run = false` is the concurrency-safe gate — never switch to select-then-insert. Dry-run rows never block live sends; failed rows DO block forever (v1: no auto-retry; delete the row manually to allow one).
- **The self-ingestion guard in `processAndIngestMessage` must never be removed:** bot replies skip the `messages` insert, so the normal telegram-id dedup can NOT catch them — without the `botSentMessageIds` check (seeded at startup from the last 24h of `bot_replies`, even when the kill switch is off) the bot's own replies re-ingest as admin replies, stamp `first_admin_reply_at`, and corrupt the Avg Response Time KPI.
- **Testing gotcha: an unquoted admin message sent via `/api/ingest` attaches to any non-admin active ticket created within the 90s window before its `msgDate`** — it returns the PARENT ticket, not a new one. To create a standalone admin ticket in tests, backdate `msgDate` to a window verified empty in the live DB (and keep it under any age guard you're testing). Also: `/api/ingest` sits behind `heavyLimiter` (5 requests / 15 min, in-memory) — restart the local server to reset it between test runs.
- **Milestone 5 is PARKED (2026-06-12): the GramJS session account is BANNED FROM SENDING in OfficialQuidaxCommunity** (`400: USER_BANNED_IN_CHANNEL` on the first live send; reading/ingestion unaffected). Keep `BOT_REPLIES_ENABLED=false`. Dry-run can structurally never catch Telegram-side permission errors — it skips the API call — so any future go-live must budget for a controlled live test. A `failed` bot_replies row blocks its (ticket, status) pair forever: (`0c72808f…`, "Awaiting User") is burned; delete the row before retrying. Never triage tickets with live mode on while sends are failing — each status change burns another pair.
- **Supabase key rotation (2026-06-12, done & verified):** production uses a new-format `sb_secret_…` key (named `railway_backend`) in the `SUPABASE_SERVICE_ROLE_KEY` var; supabase-js takes it as a drop-in. Legacy JWT keys (anon + service_role) are DISABLED — **never re-enable legacy API keys in the Supabase dashboard; that resurrects the leaked key** from public git history (verified dead, 401). The anon key was never used by production code. Also: `messages` has NO `created_at` column — use `ingested_at`/`message_timestamp` (another live-schema-vs-migrations mismatch).

Never move that stamp back above the `isMessageInTargetGroup` check. - **Anything `/api/eval` (or any deploy) needs at runtime must be a committed, non-ignored file — `benchmark_cases.json` was gitignored and never reached Railway (Fix 7, 2026-06-13, `c8b2ea9`).** The 12 gold benchmark cases now live in `benchmark-cases.ts` (a committed TS module bundled into `dist/server.mjs`), the single source of truth shared by `/api/eval` and the `eval.ts` CLI — never move benchmark data back into a gitignored JSON. The eval loop spaces Groq calls 2.1s apart (free-tier rate limit, like the verify loop); accuracy math returns `null`, never NaN, when there are no cases; the modal shows a "No benchmark cases available" empty state rather than a bare "%". `/api/eval` stays a RAW-model baseline — never add few-shot injection there. The Pidgin classification gap (§3) was closed by Fix 9 — `benchmark-cases.ts` now has 18 cases (12 English + 6 Pidgin, ids 13-18).
- **Pidgin classification uses the base system prompt, not few-shot corrections (Fix 9, 2026-06-13, `0354351`, `pidgin-glossary.ts`).** Nigerian Pidgin English phrases like "e don do", "dem block my account", "money never enter", "una too much" were falling back to General Question or getting wrong urgency. Fix: `PIDGIN_GLOSSARY_PROMPT` (phrase-mapping + 5 worked examples in the system prompt, different wording from the benchmark cases) is appended to `GROQ_SYSTEM_PROMPT` in server.ts. This is the ONLY knob that changes both `/api/eval` (raw-model baseline) and the live pipeline simultaneously — few-shot is NOT the right tool for language coverage because it requires stored corrections to fire. The benchmark was extended to 18 cases (6 new Pidgin); proven 100% Pidgin accuracy after vs 67% before. Future language-coverage gaps (e.g. Yoruba, Hausa) should follow the same pattern: a glossary section in `GROQ_SYSTEM_PROMPT`, not few-shot examples.
- **A quota/429 error is "retry much later", not "retry in a second" — don't let `isRetryableLLMError` treat them the same (Fix 8, 2026-06-13, `7a09b15`, `gemini-quota.ts`).** Gemini daily free-tier quota exhaustion was making `generateSuggestedReply` fire 3 real calls per ticket (429 counts as "retryable" → short-backoff retry), tripping the shared `geminiBreaker` (threshold 3) on every 15-min repair sweep and re-burning the already-dead quota (breaker recovers in 30s, so the next sweep re-burned again). Fix: `isQuotaExhaustedError` (429 / RESOURCE_EXHAUSTED / "quota" — but NOT a transient 503/overload, which still earns a short-backoff retry) arms a 60-min cooldown; while cooling down, `generateSuggestedReply` returns immediately after 1 failing call and the sweep skips with one log line, so nothing re-burns the quota and the breaker stays closed for the Gemini classification-fallback path. The cooldown is scoped to `generateSuggestedReply` only (the rare fallback call site is untouched — smallest change). **Always log the FULL LLM error detail (`describeLLMError`: status/statusText/errorDetails), never just `e.message`** — the original retry line logged only the message, so the failure mode (quota vs. bad model name vs. overload) could only be guessed. The reply model is `gemini-3.5-flash` while the classification fallback is `gemini-2.5-pro`; if a sweep's logged error is a 404 NOT_FOUND rather than a 429, the model name is the real bug, the cooldown (correctly) never engages, and a model change is the follow-up.

- **Phase 2 — the `getChannelDifference` live-ingestion path is BUILT and VERIFIED IN PRODUCTION (2026-06-14, `channel-difference.ts`, `CHANNEL_DIFF_ENABLED=true` permanently on Railway, deploy `d9b11b3c`).** Seeds the channel pts via `Api.channels.GetFullChannel` → `fullChat.pts`, polls `Api.updates.GetChannelDifference({ channel, filter: ChannelMessagesFilterEmpty, pts, limit: 100 })` every 15s, feeds `newMessages` into the SAME idempotent `processAndIngestMessage`, re-seeds after every watchdog reconnect. **Three response shapes (pure module `classifyChannelDifference`, switch on `className`):** `updates.ChannelDifference` (new pts = `resp.pts`, has `newMessages`), `updates.ChannelDifferenceEmpty` (pts only), `updates.ChannelDifferenceTooLong` (**new pts = `resp.dialog.pts`, and its `messages` are LATEST-STATE not the gap — NEVER bulk-ingest; re-seed the pts and let AutoFetch's 2h lookback carry the gap**). - **Railway rolling-deploy session-overlap permanently burns the GramJS session string (2026-06-16, commits `0bd0dbb` + `3a7da84`, `deploy-overlap.ts`).** Railway's rolling deploy: the NEW container starts, passes `/api/health` (Express boots ~instantly, before Telegram connects), then Railway tears down the OLD container. If the new container's `client.connect()` fires while the old one still holds the live MTProto session, Telegram responds `406: AUTH_KEY_DUPLICATED` and permanently invalidates the session string — every subsequent connect attempt also fails until you regenerate. Not transient; retrying in 10 minutes still fails. **Two-part fix — BOTH required:** (A) SIGTERM graceful-disconnect handler in `server.ts` (`process.once("SIGTERM"/"SIGINT")` → `client.disconnect()` raced against 3s timeout → `process.exit(0)`) so Railway's teardown SIGNAL fires BEFORE the new container's connect; (B) 60s startup connect delay via `TELEGRAM_CONNECT_DELAY_MS` env var (pure module `deploy-overlap.ts`, `resolveConnectDelayMs`, 12 unit tests) — the new container waits 60s before its first `client.connect()`, safely after the old container receives SIGTERM and disconnects. Default 60s; set `TELEGRAM_CONNECT_DELAY_MS=0` on a cold first deploy with no old container. The delay alone would fail if the old container is slow to disconnect; the SIGTERM handler alone would fail if Railway sends no SIGTERM (load-balancer timeout instead). Together they close the gap. Never redeploy with `numReplicas > 1` — each replica would burn the session immediately. **Post-fix verified baseline (2026-06-16):** logs show `Delaying initial connect 60s…` then `✅ Connected to Telegram (startup attempt 1)` with zero AUTH_KEY_DUPLICATED errors, pts seeded 215610, `telegramReady:true`.
